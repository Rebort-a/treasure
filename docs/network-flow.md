# 房间通信与游戏对局

## 职责与目录

- `00.common/network/protocol/`：共享的房间与消息数据、TCP 长度前缀编码和分帧；客户端与服务端均可依赖。
- `00.common/network/broadcast_discovery.dart`：局域网 UDP 发现与广播实现。
- `00.common/network/server/server_abstract.dart`：服务端 TCP / WebSocket 监听，以及单条连接的收发与关闭。
- `00.common/network/server/socket_server.dart`：房间服务逻辑，负责认证、成员事件和消息路由，不处理底层传输细节。
- `00.common/network/client/client_abstract.dart`：客户端传输选择、建连及单条连接的收发与关闭；第三方 WebSocket 依赖只在此处导入。
- `00.common/network/client/socket_client.dart`：唯一的连接所有者（A），负责认证、重连、成员表与协议收发；认证至页面创建之间按序暂存消息，不持有聊天或对局记录。
- `00.common/network/client/room_chat_engine.dart`：认证后创建的房间聊天处理器（B），持有房间聊天记录，并直接管理多人匹配候选、拒绝、超时换人和对局消息交接，不拥有连接；不再单独设置 `room_matcher.dart`。
- `00.common/network/client/game_engine.dart`：C/D 共用的局内生命周期逻辑；引擎保持不变，每局重新配置、结束并清理回调。
- `00.common/network/client/net_turn_engine.dart` / `net_real_engine.dart`：继承 `RoomChatEngine` 的回合制／实时引擎（C/D），直接处理本局规则与同步，并额外持有各自的对局聊天记录；不创建局内 session。
- `00.common/widget/component/chat_component.dart`：输入框与滚动控制器由聊天组件自行创建、监听和释放。
- `01.home/dialog.dart`：主页创建房间弹窗，以及入房表单、等待、错误展示和取消。
- `02.lan_chat/net_page.dart`：所有房间统一进入的聊天室，展示聊天和重连状态；可选注入游戏页面工厂，提供匹配卡片和成功后的跳转。
- `02.lan_chat/net_manager.dart` / `attachment_menu.dart`：聊天室导航与附件交互；附件插件集中在 `attachment_menu.dart` 导入，不再放在公共模块。
- `00.common/widget/navigator/online_game_host.dart`：通用单局生命周期容器，通过回调创建和释放 Manager、构建游戏 UI，处理返回／投降及结束后的退场；不包含聊天室，也不拥有房间连接。
- `01.home/route.dart`：装配聊天室和具体游戏的入口。聊天室与游戏彼此不导入，公共模块也不反向引用应用模块。

旧的 RoomSession 与独立 reconnect_policy 已移除。连接不因发现信息预先选择子类；认证成功后，按服务端确认的类型创建 B/C/D。成员表由连接维护，房间与对局聊天记录由相应引擎分别维护。

## 先认证，再打开聊天室

1. 主页打开入房表单；创建普通 `SocketClient`，构造时不建立连接，也不预先创建游戏引擎。发现广播必须包含非空 `key`；手动输入地址时也必须提供房间密钥。
2. 显式调用 join()，建立 Connection 并以明文发送 `connect` 类型的 `NetworkMessage`；用户名放在 `source`，密码放在 JSON `content` 中。
3. 认证通过后，服务器以明文发送 accept，内容包含 clientId、roomType、members 和必需的 key；客户端校验其与房间密钥一致，后续消息均使用该密钥进行 XOR 处理。
4. join() 只有在成功解析 accept 后才完成。失败、超时或取消均返回结构化原因并关闭连接，不打开聊天室。
5. 表单保留错误时的输入。认证成功后退出弹窗，首页统一把同一个 `SocketClient` 交给 `NetChatPage`；游戏房间额外注入名称和页面工厂，纯聊天室不注入工厂。聊天室按服务端确认的类型创建 B/C/D，不建立第二条连接；过渡期间抵达的消息由 A 补发。
6. 交接前由主页/弹窗负责关闭连接，交接后由页面持有者负责。页面已销毁或用户已取消时，迟到结果不能导航。

状态为 idle → connecting → authenticating → joined。重连也必须经过 authenticating；重新连上 Socket 不是认证成功。

初次认证失败不自动重试。已经入房后的断线使用指数退避重连，失败或取消由界面处理；旧对局立即结束，不随房间重连自动恢复。

## 房间成员事件

服务器认证通过才加入成员表并发送 `notify/join`；连接断开时发送 `notify/left`；房间停止时发送 `notify/close`。这些消息的发送者 ID 都是 0，成员事件主体位于 content 的 memberId / name 字段。

客户端不能发送 notify。服务端统一以 notify 发出 join、left、close 和 search 事件；客户端发出的 search 请求由服务端转换成 search 通知。房间引擎据此更新成员表、匹配状态和聊天记录，通知继续使用独立于玩家消息的特殊样式。

房间成员与游戏参与者不是同一份状态：退出游戏不退出聊天室；未参与游戏的房间成员不接收对局数据。

## NetworkMessage：内容与接收范围分离

| 字段 | 含义 |
|---|---|
| id | 发送者身份；0 为服务器，成员事件主体另放在内容中 |
| type | 消息语义，而非路由依据 |
| route | `room`、`private` 或 `group`；解析时与收件字段交叉校验 |
| recipientId | 私聊指定的唯一对方；由服务器先回环给发送者，再发给对方 |
| recipientIds | 群组的非空、去重收件集合，一般也包含发送者 |
| gameId | 对局 ID；首次配对时生成，实时中途加入和发布者切换沿用；房间聊天与搜索不带此字段 |
| messageId | 单包 ID；重发保持不变，ACK 和去重同时匹配 gameId 与 messageId |
| content | 消息内容；结构化内容用 JSON 编码，具体游戏资源由游戏模块解释 |
| timestamp | 必选 Unix 毫秒时间戳 |

- 房间聊天、自动通知和 search：room 范围。
- text：既能是房间消息，也能是局内私聊或群聊；表情字符与普通文字共用 text，没有独立的 emoji / typing 消息类型。
- match / confirm / reject / ack：只能私聊；publish / sync：只能指定群组；resource / action / exit：只能私聊或指定群组。
- image / file：当前仅用于房间聊天，不引入新的局内附件功能。
- 空集合、范围与字段冲突均视为非法，不会降级成广播。
- 私聊由服务器先发给发送者自己，再发给对方；群组仅按集合转发，因此需要回环时必须包含自己。发送者收到自身消息后才应用资源或行动。
- 服务端校验连接身份并使用认证名称，按集合实际转发。无关玩家不是收到数据后再丢弃，而是不会收到数据。

## 开始与取消匹配

卡片初始显示“开始匹配”。点击后留在聊天室并发送 `search` 请求；服务端回环自身原始 `search` 后显示“正在匹配”及“取消匹配”；收到回环前按钮暂不可点击，避免重复发送。服务端向新搜索者补发仍在等待的成员搜索消息，避免漏看先前的搜索。

客户端 `search` 是可重复发起的房间请求，不参与 ACK/重发；服务器原样广播并另发 `notify/search` 用于展示。匹配引擎锁定一个候选人并私聊 `match`；对方忙碌时私聊 `reject`，发起者尝试下一候选。双方同时邀请时由较小成员 ID 保持发起身份。`gameId` 标识对局，`match.messageId` 标识本次邀请，后续控制同时校验两者，旧邀请和旧局消息不能串入新事务。初始邀请无响应时尽快换人；进入确认阶段后等待至少一个完整 ACK 重发窗口。

初始匹配与实时中途入局使用同一套阶段：

```text
发起方                     应答方
match(gameId, offerId)  ──→ 预留候选
                       ←── confirm/accept
confirm/commit         ──→ 校验预留仍有效
                       ←── confirm/ready
confirm/start          ──→ 暂存即将到达的局内数据
                       ←── confirm/joined
提交名单、启动/重同步       joined 的 ACK 到达后打开对局
```

`accept` 不是已入局。发起方收到应用层 `joined` 后才提交，应答方确认自己的 `joined` 已送达后才切换页面。应用层后续确认能撤销上一阶段的重试，避免已成功入局后迟到的投递失败误伤当前对局。

取消向服务器发 `cancelSearch` 并清理本地候选/计时器；如果已预留候选，还可靠发送 `confirm/abort` 撤销该邀请，而不是发送游戏 `exit`。超时、投递失败和发布者退场同样释放预留。已撤销的邀请保留有限去重记录，迟到的 `match/start` 不能复活旧事务。服务端在 `joined` 而非 `commit` 到达时移除搜索者。仍共用一条房间连接，不创建 session 层。

### 局内消息确认与重发

`match`、`confirm`、`reject`、`publish`、`resource`、`sync`、`action`、`exit` 及定向的对局文本带 `gameId` 与 `messageId`；每位收件人回复带原 `gameId` 的私聊 `ack`。发送端按尚未确认的收件人集合指数退避重发，达到上限时报告失败；当前局内关键消息投递失败则停止该局，上一局迟到的失败通知不能中断下一局。接收端按发送者、对局、单包标识去重，对重复包再次 ACK，但只投递一次；群发需要每位其他参与者确认。房间聊天、`search`、`cancelSearch` 与 ACK 本身不重发。断线时清理本局投递状态，旧游戏不自动恢复。

`confirm` 仍保留：传输 ACK 只证明单包送达；是否接受、是否仍持有候选锁、是否已经准备入局，都由上面的应用层阶段确认。不能直接把 `match` 的 ACK 当作同意。

## 回合制：一个房间，多对独立玩家

每对玩家保留对方 ID；确认后才创建游戏管理器并配置已有引擎。资源、行动和局内聊天只私聊当前对手；游戏引擎同时校验对手身份和显式 `gameId`，拒绝同一对手上一局迟到的合法消息。游戏期间房间聊天继续由房间引擎接收并保存。

| 游戏 | 资源阶段 |
|---|---|
| 五子棋、围棋 | 匹配确认后直接行动 |
| 斗兽棋 | 先手发布初始资源，双方加载 |
| 元素战斗 | 双方在游戏页面完成各自配置，再进入行动 |

## 实时游戏：一个房间，一个共享对局

首位匹配成功的玩家成为发布者；双方完成入局事务后进入各自页面，分别处于 `frontWait` / `rearWait`。发布者为两人生成资源并向参与者集合发布。游戏继续进行时，发布者收到原始 `search`，使用当前 `gameId` 私聊邀请新玩家；收到 `joined` 后才扩充名单、重新发布资源。预留名额也计入人数上限，失败或取消后释放。未提交的邀请不暂停原有对局，不生成包含新玩家的资源。

如果新玩家的 `joined` 实际到达但所有 ACK 丢失，新玩家会发送可靠 `abort`；发布者根据邀请标识移除这一名成员并重新同步原有参与者，而不是结束原有对局。游戏结束或发布者退出会取消尚未提交的邀请。

资源快照还携带名单版本 `revision` 和已提交入局邀请记录 `admissions`。成员加入或退出时递增版本，旧快照的重发不能复活已撤销的成员。邀请记录随资源同步给其他参与者，因此原发布者在最终 ACK 前退出时，新玩家可以利用暂存资源的收件名单通知其他已知参与者撤销入局；新发布者无需依赖原发布者的内存记录。

发布者由客户端维护参与者名单并生成资源；服务器仅校验收件成员并按名单转发，不保存游戏状态。资源、同步、行动和局内文字限定在参与者集合中，旁观者收不到这些数据。发布者只有退场后才重新选举；中途加入者即使 ID 更小，发送 `action/sync` 也不能夺取当前发布者身份。胜选资源先于最后一票到达时，只接受当前名单最小 ID 的发布者接管。

游戏管理器负责资源加载和同步屏障；收到资源后进入 `synchronizing`，成员的 `sync` 都到达后才调用 `completeSynchronization()` 进入 `action`。贪吃蛇新玩家加入时重新同步，坦克最多四名参与者。

成员退出时对局暂停并重发资源。仅当退出者是记录中的发布者，余下成员才向更新后的名单发送 `publish`；收齐后选 ID 最小者发布更新后的资源，沿用本局 `gameId`。非发布者退出时由现任发布者直接重发资源。

## 模块入口与资源所有权

首页统一打开 `NetChatPage`。没有 `gamePageBuilder` 就是普通聊天室；有工厂才显示匹配卡片，游戏名称可显式传入或由已认证的房间类型推导。首页通过闭包注入具体游戏页面，聊天室不导入任何游戏模块，首页和聊天室也不实例化、释放具体游戏 Manager。

点击卡片只调用聊天引擎的 `startMatching()`；引擎负责搜索、匹配、取消和入局事务。聊天室依据 `matchPhase` 展示状态，只有入局完成才调用工厂并 push 游戏路由。六个项目的公开页面都直接继承 `StatelessWidget`，只接收 `SocketClient`，在模块内部组合 `OnlineGameHost<具体 Manager>` 与私有游戏 UI，不再继承联机页面基类。

```text
NetAnimalChessPage(room)           唯一对外入口，StatelessWidget
  └─ OnlineGameHost<NetManager>    通用生命周期容器，StatefulWidget
       └─ _AnimalChessGame        私有游戏 UI，StatelessWidget
```

Manager 的具体类型、创建与释放回调只留在游戏模块内部，不 export 给首页／聊天室，也不作为公开页面的构造参数。容器不知道具体 Manager 类型，通过 `createManager`、`engineOf`、`disposeManager` 和 `pageBuilder` 完成装配；创建回调只在 `initState` 执行一次，父页面重建只更新 UI，不重复创建或启动对局。卸载时使用创建阶段保存的释放回调配对清理。每个容器 State 对应一局，下一局通过新的游戏路由创建新 State。过渡期间的局内消息仍由引擎暂存并按序交付，不创建 session 或第二条连接。

路由层次为「首页 → 聊天室 → 单局游戏」。游戏期间下层聊天室保留，房间聊天继续写入 B 的 `messageList`，局内聊天只写入 C/D 的 `gameMessageList`。对局结束时游戏容器关闭配置子页面或对话框、返回聊天室并释放本局 Manager，不关闭引擎或连接。聊天室等待游戏路由的 `completed`，而不仅是 push 返回的 Future，确保退出动画、组件卸载和 Manager 释放完成后才允许再次匹配。

下一局重新配置同一引擎并清空对局聊天记录。回合制系统返回键和退出按钮统一弹出投降确认；实时游戏屏蔽系统返回手势，通过可见退出按钮正常退场。断线结束旧局并退回聊天室，聊天室继续展示重连状态。

认证交接后由聊天室拥有并最终释放引擎和 `SocketClient`。退出聊天室或导航栈整体卸载时，若游戏路由尚在卸载，先结束该局，等待其释放 Manager 后再销毁共享通知器。正常关闭仍限时排空已提交的发送队列，不无限阻塞退出。

## 安全与协议边界

当前面向可信局域网：握手密码为明文，发现广播或 accept 提供的 XOR 密钥不是 TLS 或端到端加密。定向路由保证转发范围，不应描述为抵御局域网监听的加密方案。

服务器不保存实时对局名单，也不承担游戏模拟。回合制由双方维护关系，接收端仍须校验对手身份。

不提供旧协议兼容，不恢复 roomControl，不引入第二条游戏连接；ACK/重发只用于局内定向消息，不用于房间发现或聊天室消息。

## 一致性边界

`gameId` 隔离不同对局，入局事务通过预留、确认和可靠撤销收敛成员名单，但不是服务端持久化事务，也不是网络分区下的强一致性协议。如果控制消息持续无法送达，系统依赖超时、断线通知和退出处理，不承诺断线续局或恢复已有游戏快照。ACK 全丢失时仍不能证明对方未处理消息，因此采用保守撤销与重同步，而不是悄悄继续推进不一致状态。
