# 房间通信与游戏对局

## 职责与目录

- `00.common/network/connection.dart`：TCP / WebSocket 字节传输、TCP 分帧和连接关闭。第三方 WebSocket 依赖只在此处导入。
- `00.common/network/engine/network_engine.dart`：房间唯一的连接所有者，负责认证、重连、成员表、房间聊天、匹配和消息分发；纯聊天房间直接使用它。
- `00.common/network/engine/net_turn_engine.dart` / `net_real_engine.dart`：继承 `NetworkEngine`；游戏房间在连接建立前选定对应类型，由其管理当前回合或实时对局会话，不另建连接。
- `00.common/network/session/`：仅在进入对局时创建的短期会话，分别处理回合消息、实时参与者与同步、局内聊天；退出对局只释放会话，房间引擎与大厅聊天继续存在。
- `00.common/network/socket_server.dart`：认证、权威成员事件和三种消息路由；不管理对局或发布者。
- `00.common/model/chat_channel.dart`：聊天组件依赖的公共接口，仅暴露身份、消息记录与发送文本能力。
- `00.common/widget/component/chat_component.dart`：输入框与滚动控制器由聊天组件自行创建、监听和释放。
- `01.home/dialog.dart`：主页创建房间弹窗，以及入房表单、等待、错误展示和取消。
- `02.lan_chat/`：通用聊天室大厅，展示聊天、匹配卡片和重连状态；由联机游戏页面嵌入，不引用具体游戏。对局期间保留大厅组件，由联机页面控制其返回键响应。

旧的 RoomSession 与独立 reconnect_policy 已移除。已发现的房间类型决定使用哪个网络引擎，认证后仍以服务端回传类型为准；动态成员表由该房间的单个网络引擎维护。

## 先认证，再打开聊天室

1. 主页打开入房表单；通过 `NetworkEngine.forRoom()` 按已发现的房间类型创建引擎，构造时不建立连接。手动输入地址尚不知道类型时先用 `NetworkEngine` 认证，再根据服务端确认的模式沿用原连接创建回合或实时会话。
2. 显式调用 join()，建立 Connection 并发送 `connect` 类型的 `NetworkMessage`；用户名放在 `source`，密码放在 JSON `content` 中。
3. 认证通过后，服务器发送 accept，内容包含 clientId、roomType、members 和 key；客户端根据 roomType 推导游戏模式和游戏人数配置。
4. join() 只有在成功解析 accept 后才完成。失败、超时或取消均返回结构化原因并关闭连接，不打开聊天室。
5. 表单保留错误时的输入。认证成功后退出弹窗，再把同一个 `NetworkEngine` 交给对应项目的 `net_page`（纯聊天房间交给 `NetChatPage`），不能建立第二条连接。
6. 交接前由主页/弹窗负责关闭连接，交接后由聊天室持有者负责。页面已销毁或用户已取消时，迟到结果不能导航。

状态为 idle → connecting → authenticating → joined。重连也必须经过 authenticating；重新连上 Socket 不是认证成功。

初次认证失败不自动重试。已经入房后的断线使用指数退避重连，失败或取消由界面处理；旧对局立即结束，不随房间重连自动恢复。

## 房间成员事件

服务器认证通过才加入成员表并发送 `notify/join`；连接断开时发送 `notify/left`；房间停止时发送 `notify/close`。这些消息的发送者 ID 都是 0，成员事件主体位于 content 的 memberId / name 字段。

客户端不能发送 notify。服务端统一以 notify 发出 join、left、close 和 search 事件；客户端发出的 search 请求由服务端转换成 search 通知。房间引擎据此更新成员表、匹配状态和聊天记录，通知继续使用独立于玩家消息的特殊样式。

房间成员与游戏参与者不是同一份状态：退出游戏不退出聊天室；未参与游戏的房间成员不接收对局数据。

## NetworkMessage：内容与接收范围分离

| 字段 | 含义 |
|---|---|
| id | 发送者身份；0 为服务器，成员事件主体另放在内容中 |
| type | 消息语义，而非路由依据 |
| route | `room`、`private` 或 `group`；解析时与收件字段交叉校验 |
| recipientId | 私聊指定的唯一对方；由服务器先回环给发送者，再发给对方 |
| recipientIds | 群组的非空、去重收件集合，一般也包含发送者 |
| content | 消息内容；结构化内容用 JSON 编码，具体游戏资源由游戏模块解释 |
| timestamp / replyToId | 可选消息元数据 |

- 房间聊天、自动通知和 search：room 范围。
- text：既能是房间消息，也能是局内私聊或群聊；表情字符与普通文字共用 text，没有独立的 emoji / typing 消息类型。
- match / confirm：只能私聊；publish / sync：只能指定群组；resource / action / exit：只能私聊或指定群组。
- image / file：当前仅用于房间聊天，不引入新的局内附件功能。
- 空集合、范围与字段冲突均视为非法，不会降级成广播。
- 私聊由服务器先发给发送者自己，再发给对方；群组仅按集合转发，因此需要回环时必须包含自己。发送者收到自身消息后才应用资源或行动。
- 服务端校验连接身份并使用认证名称，按集合实际转发。无关玩家不是收到数据后再丢弃，而是不会收到数据。

## 开始与取消匹配

卡片初始显示“开始匹配”。点击后留在聊天室并发送 `search` 请求；服务端广播包含自身成员 ID 的 `notify/search` 后，显示“正在匹配”及“取消匹配”；收到该通知前按钮暂不可点击，避免重复发送。

客户端 `search` 是发给服务器的房间请求，不带动作或请求标识。服务器将其转成 `notify/search` 广播；先搜索的一方向后搜索者私聊 `match`，后搜索者私聊 `confirm`。确认方收到自身 `confirm` 回环、发起方收到对方 `confirm` 后，双方分别创建游戏页面和引擎。

取消只清理 `NetworkEngine` 中的本地匹配状态并恢复“开始匹配”，不发送取消广播，也不创建对局会话、发送 `exit`。重新点击会重新发送 `search` 请求；服务器以 notify/search 广播匹配事件。客户端不再单独发送匹配中或退出游戏的聊天通知；加入、离开房间由服务器依据认证和断连状态通知。不引入请求 ID、对局 ID、匹配超时或并发匹配优先级。

## 回合制：一个房间，多对独立玩家

每对玩家保留对方 ID；确认后才创建游戏管理器和引擎。资源、行动和局内聊天只私聊当前对手；游戏引擎仍校验发送者身份。游戏期间房间聊天继续由房间引擎接收并保存。

| 游戏 | 资源阶段 |
|---|---|
| 五子棋、围棋 | 匹配确认后直接行动 |
| 斗兽棋 | 先手发布初始资源，双方加载 |
| 元素战斗 | 双方在游戏页面完成各自配置，再进入行动 |

## 实时游戏：一个房间，一个共享对局

首位匹配成功的玩家成为发布者；双方确认后进入各自页面，分别处于 `frontWait` / `rearWait`。发布者为两人生成资源并向参与者集合发布。游戏继续进行时，发布者收到服务器的 `notify/search`，即可私聊 `match` 并在收到 `confirm` 后扩充名单、重新发布资源。满员时不发送匹配邀请。

发布者由客户端维护参与者名单并生成资源；服务器仅校验收件成员并按名单转发，不保存游戏状态。资源、同步、行动和局内文字限定在参与者集合中，旁观者收不到这些数据。收到局内消息时，玩家仅静默以更小的成员 ID 更新所记录的发布者，不触发竞选。

游戏管理器负责资源加载和同步屏障；收到资源后进入 `synchronizing`，成员的 `sync` 都到达后才调用 `completeSynchronization()` 进入 `action`。贪吃蛇新玩家加入时重新同步，坦克最多四名参与者。

成员退出时对局暂停并重发资源。仅当退出者是记录中的发布者，余下成员才向更新后的名单发送 `publish`；收齐后选 ID 最小者发布更新后的资源。非发布者退出时由现任发布者直接重发资源。

## 模块入口与资源所有权

首页路由直接打开对应项目的 `net_page(room: room)`；纯聊天房间直接打开 `NetChatPage`。六个项目页面均继承 `OnlineGamePage`（仍是 `StatelessWidget`），各自只暴露这一个联机页面路由；纯聊天页不是游戏页面，不继承它。首页和聊天室都不导入、实例化或释放具体游戏 Manager。

点击大厅卡片只调用 `NetworkEngine.startMatching()`；引擎负责搜索、回环确认、私聊匹配及取消，并记录对手与发起方。聊天室仅依据 `matchPhase` 展示状态；确认后由 `OnlineGamePage` 的共用容器创建项目 Manager，通过房间对应的 `NetTurnEngine` / `NetRealEngine` 创建局内会话，并在同一路由内展示项目提供的对局组件。没有 `MatchSession` 或 `MatchResult` 包装对象。对局组件尚未接管时到达的消息由房间引擎暂存，会话注册后按顺序交付。

匹配期间只有房间网络引擎，没有游戏 Manager 或对局会话。匹配完成后仍在原联机页面内切换大厅和对局组件，不创建第二条页面路由；对局结束后释放本局 Manager 并重新显示保留的大厅，房间聊天记录不丢失。实时游戏在对局组件中等待资源与同步。回合游戏系统返回键和投降按钮统一弹出投降确认；实时游戏屏蔽系统返回手势，由可见退出按钮执行正常退场。

交接后由联机页面负责关闭和销毁房间的 `NetworkEngine`（包括回合、实时子类）；局内会话只订阅房间消息，退出对局时释放会话而不关闭房间连接。正常关闭时尝试限时排空已提交的发送队列，不无限阻塞退出。

## 安全与协议边界

当前面向可信局域网：握手密码为明文，发现广播或 accept 提供的 XOR 密钥不是 TLS 或端到端加密。定向路由保证转发范围，不应描述为抵御局域网监听的加密方案。

服务器不保存实时对局名单，也不承担游戏模拟。回合制由双方维护关系，接收端仍须校验对手身份。

不提供旧协议兼容，不恢复 roomControl，不引入第二条游戏连接或通用 ACK 重试机制。
