# 房间与游戏会话

## 一条连接，两个生命周期

```text
房间列表 → NetworkEngine（唯一长连接）→ NetChatPage
                                      │
                               点击 Click to play
                                      │
                         GameLaunch 创建管理器和游戏引擎
                         GameStep.start → search + notify
                                      │
                       匹配成功／实时游戏完成全员同步
                                      │
                         将已有管理器交给游戏页面
                                      │
                          结束游戏 → 返回聊天室
```

- `NetworkEngine` 负责连接、身份、成员快照和完整房间聊天记录。
- `NetGameEngine` **不继承 `NetworkEngine`，不创建 Socket**，而是订阅已有房间连接。
- `NetTurnGameEngine` 和 `NetRealGameEngine` 只实现对局协议。
- `ChatChannel` 位于 `00.common/chat/chat_channel.dart`，是引擎和聊天组件共用的聊天展示与输入接口，不属于引擎实现或底层网络协议。房间聊天和对局私聊各自持有消息列表、输入框、滚动控制器。
- `GameLaunch` 位于 `00.common/widget/navigator/game_launch.dart`，在匹配阶段持有管理器；页面只使用注入的管理器。页面退出动画完成后再释放管理器，重复释放不会重复销毁。
- 首页路由装配具体游戏，并向聊天室注入 `GameLaunchFactory`。聊天室不导入首页路由或具体游戏模块。

## 发现与入房

服务器每次 UDP 广播都重新构建 `MessageType.broadcast`，带房间名、类型、端口、密钥、密码标记及当前已认证连接数。

客户端连接后提交名称和可选密码。认证通过后，服务器单发：

```json
{
  "id": 0,
  "type": "<MessageType.accept>",
  "source": "<房间名称>",
  "content": "{\"clientId\":1,\"roomType\":3,\"key\":\"...\"}"
}
```

`accept` 本身不加密，提供后续通信的密钥，因此通过 IP 加入不需要预先请求 HTTP 元数据或选择类型。密码不会出现在房间广播中。

旧的 `http_fetch.dart`、`http` 直接依赖及普通 HTTP 房间信息查询接口已删除。WebSocket 仍使用 HTTP 升级握手；非升级请求返回 404。锁文件中的 `http` 仍可能作为其他插件的间接依赖存在。

### 安全边界

当前面向可信局域网：密码用于入房校验，握手直接发送密码，房间密钥通过发现广播或 `accept` 提供。这不是 TLS 或端到端加密方案，不应把密码房间理解为能防御局域网监听。若需要不可信网络下的安全性，应单独设计安全传输、身份认证和密钥分发，不在本次流程清理中临时拼接。

客户端处理 `accept` 后在房内广播加入通知。服务器使用 `roomControl` 发布成员快照；它不保存游戏席位或游戏连接令牌。未指定 `targetId` 的客户端消息广播给房内成员；指定后只发给目标。

### 自动通知与本地化

`MessageType.notify` 的 `content` 仅传 `RoomNotice` 的固定编码字符串，不发送翻译后的完整文本：

| 编码 | 枚举 | 含义 |
|---|---|---|
| `"1"` | `joinedRoom` | 加入房间 |
| `"2"` | `leftRoom` | 离开房间 |
| `"3"` | `matchingPlayers` | 正在匹配 |
| `"4"` | `leftGame` | 退出游戏 |

发送者名称仍放在 `source` 中。聊天记录保留原始编码，界面渲染时按接收方当前语言翻译，因此切换语言后已有通知也会更新。普通 `text` 消息及用户名保持原样；未知编码和旧版完整文本通知会被丢弃，不作为文案直接显示。

## 点击与重复点击

置顶卡片只有游戏类型和 `Click to play`。首次点击创建游戏管理器及引擎并发送 `search` 和匹配通知，不立即跳转页面。

等待期间再次点击会结束旧的等待会话、创建新会话，再发送搜索和通知。每次会话有新的 `requestId`，匹配后使用共同的 `sessionId`，防止旧对局消息进入新对局。这些标识不是 ACK 或消息重试 ID。

搜索消息经过服务器回环。引擎只响应排在自身搜索回环之后的其他玩家搜索，避免两个同时发起的搜索都自认为先手。

## 回合制

先手记录对手并定向发送 `match`；后手在 `start` 阶段验证搜索请求、记录对手，然后双方允许打开页面。

| 游戏 | 资源模式 | 流程 |
|---|---|---|
| 五子棋、围棋 | `none` | 匹配后直接 `action`，不发送占位 `resource` |
| 斗兽棋 | `frontOnly` | 先手生成棋盘；双方接收该棋盘后 `action` |
| 元素战斗 | `both` | 先手 `frontConfig → frontWait → action`；后手 `rearWait → rearConfig → action` |

对局行动、资源、文字及表情私发给对手；需要本地执行的消息另发给自身，统一经服务器回环处理。图片、附件不能发进对局。房间公开聊天继续由 `NetworkEngine` 收集，不混入对局私聊。

## 实时游戏

搜索阶段先假定自己是发布者；收到发布者资源后跟随该发布者。发布者负责参与者名单、入场资源及人数上限；坦克最多四人，超额请求等待空位。

资源包携带参与者列表。只有列入其中的当前会话才加载资源，普通聊天成员不会创建游戏画面。游戏管理器维护同步屏障：收到本次资源的所有参与者的 `sync` 后，调用 `completeSynchronization()`，首次才允许打开游戏页面。仅收到资源不等于可以运行游戏。

贪吃蛇新玩家加入时仍全员重载资源、蛇身仅保留头部。发布者离开后，参与者从共享名单中选出最小 ID 作为继任者。

## 结束与清理

- 游戏退出、投降或对手离开：发送对局 `exit`，移除游戏消息订阅，停止实时游戏计时器，返回聊天室；**不关闭房间 Socket**。
- 五子棋、围棋、斗兽棋结束直接返回聊天室；元素战斗和坦克保留结果提示，确认后退出，无联机重开按钮。
- 再玩一局仍从聊天室点击卡片，使用新的管理器和会话。
- 只有离开聊天室才关闭房间连接。实际断线会结束当前对局并触发房间重连，不自动恢复旧对局。
- `NetworkEngine.closeSocket()` 只负责幂等地关闭连接，阻止新发送并清空已有发送队列；`leavePage()` 额外请求一次页面退出；聊天室持有者在 `dispose()` 中释放控制器、消息监听器和通知器。游戏结束只释放游戏会话，不销毁房间引擎。
- 连接关闭时同时取消接收订阅，连接尚未建立就销毁页面时，迟到的连接会立即关闭。导航通知器按事件消费命令，不再在空闲状态反复安排帧。
- 不包含 ACK、超时重发、观战画面、第二条游戏连接或服务器席位令牌。

回归测试覆盖协议、资源阶段、同步屏障、多对局聊天隔离、重复点击、旧会话消息、贪吃蛇重同步、坦克人数上限，以及游戏页面返回后的房间连接和消息保留。
